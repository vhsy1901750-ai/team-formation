# PRD: 팀 프로젝트 팀 편성 웹 앱

## 1. 배경과 목적

수업의 팀 프로젝트를 위해 학생들이 스스로 팀을 꾸리는 웹 앱이다. 학생은 팀에 지원하고, 팀원들이 투표로 받아들일지 정한다. 모집을 마감한 뒤 팀이 없는 학생은 AI가 배정안을 내고, 앱이 그 배정안이 규칙을 지키는지 검사한다. AI가 끝내 실패하면 앱이 직접 배정한다.

이 앱은 중간 과제(30점)이며, 채점은 자동 채점 프로그램이 배포한 앱의 화면을 Streamlit `key`로 찾아 조작하는 방식이다. 따라서 **화면 요소의 key와 결과 안내의 첫 단어가 공고와 정확히 같아야 한다.**

## 2. 사용자

| 사용자 | 로그인 | 하는 일 |
|---|---|---|
| 학생 | 학번, 비밀번호(모두 `1234`) | 팀 목록과 팀원, 역할을 봄. 팀에 지원함. 내 팀에 들어온 지원에 찬성 또는 거부를 누름 |
| 관리자(교수) | 학번 `admin`, 비밀번호는 비밀 값 `ADMIN_PASSWORD` | 명단을 올려 처음 상태를 만듦. 모집을 마감함. 남은 학생의 배정안을 받아 확인하고 확정함 |

학생은 교수가 나눠 준 가상 명단의 학생이다. 실제 사람의 이름과 학번은 쓰지 않는다.

## 3. 목표, 비목표

**목표**
- 공고의 규칙(2장)을 빠짐없이 지키고, 3장 표의 기능을 모두 **어려운 해결**로 만든다.
- 채점 프로그램이 멈추지 않도록 2.7절 화면 이름 표의 key를 그대로 쓴다.
- 채점 기간(11/3~11/4)에 DB가 일시정지되지 않게 한다.

**비목표** (만들지 않는 것)
- 회원 가입, 구글 로그인(`st.login`), 비밀번호 바꾸기
- 학생의 역할 바꾸기, 팀 탈퇴, 투표 바꾸기
- 지원 취소 (공고에 없음)
- 꾸민 화면, 모바일 전용 화면

**실패로 보는 것** (기능이 돌아가도 실패)
- 키나 관리자 비밀번호가 코드, 깃허브, 화면에 드러남
- 연습 시나리오의 학생 이름이나 순서를 보고 결과를 미리 정해 둔 코드
- AI 배정이 10분 넘게 끝나지 않음

## 4. 기능 요구 사항

### 4.1 로그인

- 학번과 비밀번호로 로그인한다. 비밀번호는 bcrypt 해시로 저장하고 비교한다.
- 비밀번호가 틀리거나 없는 학번이면 로그인되지 않고 "막힘: 학번이나 비밀번호가 틀림"을 보여 준다.
- 로그인하면 `whoami`에 이름(관리자는 "관리자")을 보여 준다. 로그아웃 단추를 둔다.
- 앱이 시작할 때 `ADMIN_PASSWORD`로 관리자 계정을 만들거나, 비밀번호가 바뀌었으면 해시를 갱신한다. 명단을 다시 올려도 관리자 계정은 남긴다.
- 학생 계정으로는 관리자 화면과 관리자 기능을 쓸 수 없다. 화면을 숨기는 것과 별도로, 관리자 동작을 처리하는 함수에서도 관리자인지 다시 확인한다.

### 4.2 명단 올리기 (관리자)

- CSV 파일과 팀 수를 넣고 "처음 상태 만들기"를 누르면 지원, 투표, 팀원, 마감 표시, 배정안, 학생을 모두 지우고(관리자 제외), 명단의 학생과 팀 수만큼의 빈 팀(팀1, 팀2, …)을 만든다.
- CSV는 `utf-8-sig`로 읽는다(BOM이 있어도 읽음). 열은 `student_no,name,main_role,sub_roles`이고, 보조 역할은 `;`로 구분하며 없으면 빈칸이다. 값 앞뒤의 공백은 지운다.
- 역할이 6개(기획자, 웹 프로그래머, 프론트엔드 디자이너, 테스터, 보고서 작성자, 발표자) 밖이거나 열이 모자라면 아무것도 바꾸지 않고 "막힘: 이유"를 보여 준다.
- 학생 비밀번호 `1234`도 해시로 저장한다.

### 4.3 학생 화면

- 팀마다 팀 이름, 팀원의 이름, 주 역할, 보조 역할을 보여 준다(`team_1`, `team_2`, …). 내 팀에는 "내 팀"을 붙이고, 팀이 없으면 "아직 팀이 없음"을 보여 준다.
- 팀마다 지원 단추(`apply_1`, …)를 둔다. 이미 팀이 있거나, 결과를 기다리는 지원이 있거나, 모집이 마감되었으면 지원 단추를 비활성화한다.
- 내 팀에 들어온 대기 중인 지원마다 지원자 이름, 역할과 찬성, 거부 단추(`vote_yes_{학번}`, `vote_no_{학번}`)를 보여 준다. 이미 투표한 지원은 단추를 비활성화하고 "내 투표: 찬성"처럼 보여 준다.
- 내가 낸 지원이 대기 중이면 어느 팀에 지원했는지 보여 준다.

### 4.4 지원

지원 단추를 누르면 아래 순서로 검사하고, 처음 걸리는 이유로 막는다. 막힌 지원은 DB에 기록하지 않는다.

| 순서 | 막는 이유 | 안내 |
|---|---|---|
| 1 | 모집이 마감됨 | 막힘: 모집이 마감됨 |
| 2 | 이미 팀이 있음 | 막힘: 이미 팀이 있음 |
| 3 | 결과를 기다리는 지원이 있음 | 막힘: 결과를 기다리는 지원이 있음 |
| 4 | 팀이 4명으로 꽉 참 | 막힘: 팀이 꽉 참 |
| 5 | 주 역할이 같은 팀원이 있음 | 막힘: 같은 주 역할의 팀원이 있음 |
| 6 | 필수 포함 역할을 맡을 학생의 자리가 모자람(5.2절) | 막힘: 필수 포함 역할을 맡을 학생의 자리가 모자람 |

1~3은 단추를 비활성화해 두지만, 같은 검사를 서버 쪽에서도 다시 한다.

통과하면:
- **빈 팀**: 바로 팀원이 된다. "승인: 팀N의 팀원이 됨"
- **팀원이 있는 팀**: 대기 상태로 접수한다. "대기: 팀원의 투표를 기다림"

### 4.5 투표와 승인

- 투표할 사람은 **투표하는 때의 팀원**이다. 지원한 뒤에 다른 지원자가 먼저 팀원이 되면 그 사람도 투표해야 한다.
- 한 명이라도 거부하면 다른 투표를 기다리지 않고 바로 거절한다. "거절: 팀원이 거부함"
- 그 순간의 팀원 모두가 찬성했으면 승인하기 직전에 4.4절의 4~6번 검사(정원, 주 역할 중복, 필수 포함 역할 자리)를 그 순간의 팀 구성으로 다시 한다.
  - 통과하면 승인하고 팀원으로 넣는다. "승인: 팀N의 팀원이 됨"
  - 걸리면 거절한다. "거절: 승인 직전 검사에서 같은 주 역할의 팀원이 있음"처럼 이유를 붙인다.
- 아직 투표하지 않은 팀원이 있으면 대기로 둔다. "대기: 다른 팀원의 투표를 기다림"
- 처리 순서는 지원한 순서가 아니라 **투표가 끝난 순서**다. 투표 하나를 처리할 때마다 그 지원의 결과를 바로 정하므로 자연히 이 순서가 된다.
- 팀이 바뀌어도 대기 중인 지원을 미리 거절하지 않는다. 승인하려는 순간에만 다시 검사한다.
- 투표는 한 번만 할 수 있고 바꿀 수 없다.
- 투표를 막는 경우: 모집이 마감됨, 이미 투표함, 그 팀의 팀원이 아님. 지원이 이미 승인이나 거절로 끝났으면 투표하지 않고 그 결과를 보여 준다.
- 찬성, 거부 단추를 누른 사람의 `result`에는 그 지원의 지금 상태(승인, 대기, 거절)를 보여 준다.

### 4.6 모집 마감 (관리자)

- "모집 마감"을 누르면 마감 표시를 하고, 대기 중인 지원을 모두 거절한다("거절: 모집 마감").
- 팀원이 1명뿐인 팀의 학생은 팀에서 빼서 "팀이 없는 학생"으로 만든다.
- 마감 뒤에는 지원과 투표를 할 수 없다.
- 관리자 화면의 `unassigned`에 팀이 없는 학생의 이름을 보여 준다.
- 이미 마감했으면 "막힘: 이미 마감됨".

### 4.7 배정과 확정 (관리자)

"AI 배정"을 누르면 다음 순서로 진행한다.

1. **마감 확인**: 마감 전이면 "막힘: 모집이 마감되지 않음".
2. **사전 검사**: 앱의 배정 함수(5.3절)로 규칙을 지키는 배정이 있는지 먼저 끝까지 찾는다. 없으면 AI를 부르지 않고 `assign_status`에 "규칙을 지키는 배정이 없음"과 이유(예: "팀3에 웹 프로그래머를 맡을 학생이 없음")를 보여 준다.
3. **AI 1차, 2차, 3차**: 오픈라우터의 무료 텍스트 생성 모델 3개를 차례로 부른다. 모델마다 부른 때부터 응답을 다 받을 때까지 **전체 120초**를 재서, 넘으면 끊고 다음 모델로 넘어간다. 아래 경우는 모두 실패로 보고 다음 모델로 넘어간다.
   - 120초 넘음, HTTP 오류(429 포함), 연결 오류
   - 빈 응답, JSON으로 읽을 수 없는 응답
   - 배정안이 5.4절의 검사 다섯 가지 가운데 하나라도 통과하지 못함
4. **앱이 스스로 배정**: 3차까지 실패하면 2번에서 찾은 배정을 쓴다. 모든 경우를 따져 찾은 것이므로 검사 다섯 가지를 반드시 통과한다.
5. **보여 주기**: 검사를 통과한 배정안만 보여 준다(학생 이름, 역할, 배정된 팀). 어느 모델이 낸 배정안인지, 앞 모델들이 왜 실패했는지도 함께 보여 준다.
6. **확정**: "배정안 확정"을 누르면 배정안을 DB에 저장한다. 저장하기 직전에 배정안이 여전히 규칙을 지키는지 다시 검사한다. "승인: 배정을 확정함"

AI를 기다리는 동안 `assign_status`에 "2차 모델(모델 이름)의 응답을 기다리는 중 (35초)"처럼 몇 차 모델인지와 지난 시간을 보여 준다.

이미 팀에 있는 학생은 옮기지 않는다. 배정은 팀이 없는 학생만 팀에 넣는다.

관리자 화면에도 학생 화면과 같은 팀 목록(`team_1`, …)을 보여 준다. 명단 파일 없이 "처음 상태 만들기"를 누르거나 확정할 배정안이 없는데 "배정안 확정"을 누르면 "막힘: 이유"를 보여 준다.

### 4.8 다른 사람의 변경 보기

- 학생 화면과 관리자 화면의 팀 목록, 지원 목록, 팀이 없는 학생 표시를 `st.fragment(run_every=3)`으로 3초마다 다시 그린다. 공고의 기준은 5초 이하다.
- 새로 고침 단추는 두지 않는다(어려운 해결을 고르면 필요 없음).

## 5. 규칙 정의

### 5.1 팀 규칙 (2.3절)

- 팀 수는 명단을 올릴 때 관리자가 정한다.
- 확정한 팀 구성에서는 모든 팀이 2~4명이다(빈 팀 없음).
- 주 역할이 같은 학생이 한 팀에 2명 이상이면 안 된다.
- 모든 팀에 기획자와 웹 프로그래머를 맡을 학생이 **서로 다른 사람으로** 1명씩 있어야 한다. 주 역할이나 보조 역할로 맡을 수 있다.

### 5.2 필수 포함 역할 자리 계산

- **채운 필수 역할 수**: 팀원(지원자 포함)과 {기획자, 웹 프로그래머}를 짝지을 때 최대로 짝지을 수 있는 수(0~2). 한 학생이 둘 다 할 수 있어도 한 역할만 맡는다.
- **못 채운 필수 역할 수** = 2 − 채운 필수 역할 수
- **남는 자리 수** = 4 − (지금 팀원 수 + 1)
- 남는 자리 수 < 못 채운 필수 역할 수 이면 막는다.

예: 테스터와 발표자만 있는 팀(2명)에 보고서 작성자가 지원하면, 남는 자리 1개로 못 채운 2개를 채울 수 없으므로 막는다.

### 5.3 앱이 스스로 하는 배정

팀이 없는 학생(최대 8명)을 팀(3~4개)에 넣는 모든 경우를 되추적(백트래킹)으로 끝까지 따져, 5.4절의 검사를 모두 통과하는 배정을 하나 찾는다. 경우의 수가 많아야 4^8 = 65,536이라 금방 끝난다. 주 역할이 겹치거나 팀이 4명을 넘으면 그 갈래는 더 따지지 않는다. 학생 이름을 보고 정하는 규칙은 두지 않는다.

배정이 없을 때 보여 줄 이유는 다음을 차례로 확인해 찾는다.
- 학생 수가 팀 수 × 2보다 적거나 팀 수 × 4보다 많음
- 이미 4명인 팀에 기획자나 웹 프로그래머를 맡을 학생이 없음
- 어떤 팀에 넣을 수 있는 학생(주 역할이 겹치지 않는 학생) 가운데 그 팀에 모자란 필수 역할을 맡을 학생이 없음
- 위에 해당하지 않으면 "모든 경우를 따져 보았지만 규칙을 지키는 배정이 없음"

### 5.4 배정안 검사 다섯 가지 (2.5절 4항)

1. 팀이 없는 학생이 빠짐없이 배정됨 (모르는 학번이나 이미 팀이 있는 학생이 들어 있으면 실패)
2. 한 학생은 한 팀에만 배정됨
3. 모든 팀이 2~4명
4. 팀 안에서 주 역할 중복 없음
5. 모든 팀이 필수 포함 역할을 충족함

## 6. 고른 해결 방법 (3장 표)

| 기능 | 고른 해결 | 만드는 방법 |
|---|---|---|
| 다른 사람의 변경 보기 | 어려운 해결 | `st.fragment(run_every=3)` |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운 해결 | 지원 단계에서 5.2절 계산으로 막음 |
| 같은 팀에 대기 중인 지원이 여럿 | 어려운 해결 | 모든 팀원이 찬성한 순간 4.4절 4~6번을 다시 검사 |
| 마지막 자리에 두 명이 동시에 들어감 | 어려운 해결 | `tf_members`의 `(team_id, slot_no)` 기본 키와 `student_id` 유일성 제약. 제약에 걸리면 먼저 기록된 학생만 남고 늦은 쪽은 막힘이나 거절 |
| AI 응답이 늦을 때 | 어려운 해결 | 모델마다 별도 스레드로 부르고 전체 120초가 지나면 기다리기를 그만두고 다음 모델로 넘어감 |
| 3차 모델까지 실패 | 어려운 해결 | 5.3절의 되추적 배정 |
| AI 대기 중 화면 | 어려운 해결 | 몇 차 모델인지, 모델 이름, 지난 시간을 1초마다 갱신 |
| DB 일시정지 막기 | 어려운 해결 | 깃허브 액션 예약 작업으로 매일 DB에 질의 |

## 7. 화면 요소와 key (2.7절)

| 화면 요소 | Streamlit 요소 | key |
|---|---|---|
| 학번 입력칸 | `st.text_input` | `login_student_no` |
| 비밀번호 입력칸 | `st.text_input` | `login_password` |
| 로그인 단추 | `st.button` | `login_submit` |
| 로그인한 사람 표시 | `st.container` | `whoami` |
| 단추를 누른 결과 안내 | `st.container` | `result` |
| 팀 하나의 표시 | `st.container` | `team_1`, `team_2`, … |
| 팀에 지원하는 단추 | `st.button` | `apply_1`, `apply_2`, … |
| 지원에 찬성 | `st.button` | `vote_yes_{지원자 학번}` |
| 지원에 거부 | `st.button` | `vote_no_{지원자 학번}` |
| 명단 CSV 올리기 | `st.file_uploader` | `admin_roster_file` |
| 팀 수 | `st.number_input` | `admin_team_count` |
| 처음 상태 만들기 | `st.button` | `admin_start` |
| 모집 마감 | `st.button` | `admin_close` |
| 팀이 없는 학생 표시 | `st.container` | `unassigned` |
| AI 배정 | `st.button` | `admin_assign` |
| AI 배정 진행 안내 | `st.container` | `assign_status` |
| 배정안 확정 | `st.button` | `admin_confirm` |

- `result`에 보여 줄 문장은 세션 상태에 저장해 두고, 화면을 다시 그릴 때마다(3초마다 포함) 그대로 다시 보여 준다. 그래야 자동으로 다시 그려도 안내가 사라지지 않는다.
- `result`의 첫 단어는 "승인", "대기", "거절", "막힘" 가운데 하나다. 관리자 단추의 결과도 같다(예: "승인: 모집을 마감함").
- 한 학생의 대기 중인 지원은 최대 1개이므로 `vote_yes_{학번}` key가 한 화면에서 겹치지 않는다.

## 8. 데이터 (Supabase, 모든 테이블은 `tf_`로 시작)

| 테이블 | 열 | 제약 |
|---|---|---|
| `tf_students` | `id`, `student_no`, `name`, `main_role`, `password_hash`, `is_admin` | `student_no` 유일. `main_role`은 6개 역할 가운데 하나(관리자는 비움) |
| `tf_student_sub_roles` | `student_id`, `role` | `(student_id, role)` 기본 키. `role`은 6개 역할 가운데 하나 |
| `tf_teams` | `id`, `team_no`, `name` | `team_no`, `name` 유일 |
| `tf_members` | `team_id`, `slot_no`, `student_id` | `(team_id, slot_no)` 기본 키, `student_id` 유일, `slot_no between 1 and 4` |
| `tf_applications` | `id`, `team_id`, `student_id`, `status`, `reason`, `created_at`, `decided_at` | `status`는 대기, 승인, 거절. 학생마다 대기 중인 지원은 1개만(부분 유일 인덱스) |
| `tf_votes` | `application_id`, `voter_id`, `vote`, `created_at` | `(application_id, voter_id)` 기본 키. `vote`는 찬성, 거부 |
| `tf_settings` | `key`, `value` | 마감 여부, 확정 전 배정안(JSON), 마지막 예약 질의 시각 |
| `tf_ai_logs` | `id`, `created_at`, `attempt`, `model`, `outcome`, `detail`, `elapsed_ms` | AI 호출 기록. README 5항(실패 사례)의 근거로 씀 |

- 테이블을 만드는 SQL은 저장소의 `schema.sql`에 둔다.
- 팀원을 넣을 때는 비어 있는 가장 작은 `slot_no`를 골라 넣는다. 동시에 들어와 제약에 걸리면 먼저 기록된 학생만 남는다.
- 시각은 DB에 UTC로 저장하고, 화면에는 한국 시각으로 바꿔 보여 준다.

## 9. 기술 선택

| 항목 | 선택 | 이유 |
|---|---|---|
| 언어 | Python 3.12 | 이 컴퓨터에 설치되어 있음 |
| 화면 | Streamlit (최신판) | 공고가 정함. `st.container(key=...)`와 `st.fragment`가 필요 |
| DB 연결 | psycopg 3 + `psycopg_pool` | `DATABASE_URL`(Session pooler 주소)로 바로 연결. 연결 묶음을 `st.cache_resource`로 한 번만 만들어 다시 씀(4.2절 공고 요구) |
| 비밀번호 해시 | bcrypt | 공고가 예로 든 방법 |
| AI 호출 | `requests`로 오픈라우터 API 직접 호출 | 모델마다 시간 제한과 넘어가기를 직접 만들어야 하므로 |
| 키 읽기 | 내 컴퓨터는 `.env`(python-dotenv), 배포한 앱은 Streamlit Secrets | 공고가 정함 |
| 테스트 | pytest, Streamlit `AppTest` | 규칙 함수는 DB 없이 시험하고, 연습 시나리오는 화면 key로 자동 실행 |

AI 모델 3개는 구현할 때 오픈라우터의 무료 모델 목록에서 실제로 응답하는 것을 시험해 고른다. 한 회사 모델이 한꺼번에 막히지 않도록 서로 다른 회사의 모델로 고른다. `openrouter/free` 라우터는 쓰지 않는다. 추론 모델은 `reasoning effort`를 low로 주고 `max_tokens`를 넉넉히 준다.

## 10. 키 관리와 보안

- `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`는 `.env`(내 컴퓨터)와 Streamlit Secrets(배포)에만 둔다. `.env`는 `.gitignore`로 깃허브에 올리지 않는다.
- 코드는 키 값을 화면이나 로그에 출력하지 않는다. 키가 있는지 확인할 때는 "있음, 없음"만 출력한다. DB 오류 안내에도 주소가 섞이지 않게 한다.
- 비밀번호는 해시로만 저장한다.

## 11. 배포와 운영

- 깃허브 비공개 저장소에 올리고 Streamlit Community Cloud에 배포한다. 배포 뒤 앱을 공개로 바꾸고 시크릿 창에서 로그인 화면이 보이는지 확인한다.
- **DB 일시정지 막기**: 깃허브 액션 예약 작업(`.github/workflows/keepalive.yml`)이 매일 한 번 DB에 질의하고 `tf_settings`에 시각을 기록한다. 저장소 Secrets에 `DATABASE_URL`을 넣어야 한다. 손으로 돌려 볼 수 있게 수동 실행도 연다.
- 마감(11/2 23:59) 뒤에는 커밋하지 않는다. 11/3 09:00까지 저장소를 공개로 바꾼다.
- 채점 기간에는 관리자 비밀번호를 바꾸지 않고, 오픈라우터 하루 한도 가운데 30번 이상을 남겨 둔다.

## 12. 검증 방법

| 무엇을 | 어떻게 |
|---|---|
| 규칙 함수(지원 검사, 필수 역할 계산, 배정안 검사, 되추적 배정) | pytest 단위 테스트. DB 없이 실행 |
| 연습 시나리오 3개(쉬움, 중간, 어려움) | `AppTest`로 학생마다 따로 로그인해 단계를 차례로 실행하고, `result` 첫 단어가 기대 결과와 같은지 확인. 실제 Supabase DB 사용 |
| AI 실패 처리 | AI 호출 함수를 가짜로 바꿔 시간 초과, 429, 빈 응답, 규칙을 어긴 배정안을 차례로 내게 하고, 2차, 3차, 앱 배정으로 넘어가는지 확인 |
| 실제 AI | 내 컴퓨터와 배포한 앱에서 몇 번만 실제로 불러 봄(하루 50회 한도 아껴 쓰기) |
| 배포 | 배포한 앱을 시크릿 창으로 열어 연습 시나리오를 직접 해 보고 README 사례의 화면을 캡처 |

연습 시나리오를 통과하는 것은 목표가 아니라 확인 수단이다. 채점은 다른 명단과 순서로 하므로, 규칙을 일반적으로 구현했는지가 중요하다.

## 13. 위험과 대응

| 위험 | 대응 |
|---|---|
| 3초마다 다시 그리는 동안 AI 배정(최대 6분)이 끊김 | AI 배정 단추와 진행 안내는 자동으로 다시 그리는 영역 밖에 둔다. 구현할 때 실제로 끊기지 않는지 먼저 시험한다 |
| 3초마다 다시 그려 화면이 느림 | 연결 묶음을 다시 쓰고, 한 번 그릴 때 질의 수를 줄인다 |
| Supabase Direct connection은 IPv6 전용이라 Streamlit 서버에서 접속 안 됨 | Session pooler 주소를 쓴다 |
| 무료 모델이 채점 때 모두 실패 | 앱 배정(5.3절)이 반드시 규칙을 지키는 배정을 낸다 |
| 화면에 보이는 문장이 바뀌어 채점 실패 | 채점은 key와 첫 단어만 보므로, 첫 단어를 상수로 정해 한곳에서 씀 |

## 14. 만들면서 정한 것 (내가 정함, 확인 필요)

- 3장의 기능은 모두 어려운 해결로 만든다. (사용자가 정함)
- 지원 단추는 2.8절의 세 경우(팀 있음, 대기 지원 있음, 마감)에만 비활성화하고, 나머지 막힘은 단추를 눌렀을 때 "막힘: 이유"로 안내한다.
- 확정 전 배정안은 `tf_settings`에 저장해 화면을 다시 그려도 남게 한다.
- 다시 그리는 간격은 3초로 한다.
- DB 일시정지 막기는 깃허브 액션으로 한다. 외부 사이트에 DB 주소를 맡기지 않아도 되기 때문이다.
- 저장소 폴더는 `C:\test`를 그대로 쓴다.
